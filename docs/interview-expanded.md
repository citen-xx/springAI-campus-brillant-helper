# 校园智能知识库助手项目面试扩展手册

说明：
- 本手册只基于当前仓库代码、现有测试文档和已确认的运行时结论整理。
- 没有真实验证过的能力，一律不按“已验证”表达。
- 没有真实压测结果，一律不写具体 QPS、P99、首字响应数据。
- student chat 当前口径固定为“单次工具分发 + SSE 单条回推”，不是逐 token 工具流。
- 知识库删除当前口径固定为“代码实现 + 失败场景验证”，不是完整成功链路已运行时验收。

## 1. 项目一句话定位

### 1.1 极简版
这是一个把 AI 问答接进校园业务系统，并补齐权限、稳定性和数据治理的工程化后端。

### 1.2 Java 后端版
这是一个校园智能问答后端，我重点做了权限链路、SSE 连接治理和知识库删除闭环。

### 1.3 AI 应用后端版
这是一个把知识库问答和工具调用落进真实业务，并把边界做实的 AI 应用后端。

### 1.4 权限安全版
这不是普通聊天 demo，而是把学生查自己、管理员查全量两条链路明确拆开的 AI 系统。

### 1.5 面试开场版
我做的重点不是接模型，而是把模型安全接进业务：既能问知识库，也不会越权查别人数据。

## 2. 项目核心主线扩写

### 2.1 30 秒版
这个项目我不会把它讲成一个普通 AI 聊天 demo，因为我主要做的不是“把模型接上”，而是把它放进真实业务系统里。围绕这个目标，我补了五块工程能力：RAG 问答、学生工具调用权限、学生和管理员的安全边界、SSE 断连取消，还有知识库删除时的数据闭环。所以它更像一个 AI 应用后端工程题。

### 2.2 1 分钟版
这个项目本质上是一个校园智能问答后端，但我做的重点不是模型效果包装，而是工程化补强。公共问答这条链路我接了 RAG，让模型能基于校内知识回答问题。个人数据这条链路我没有信任前端或者模型传进来的 `studentId`，而是统一从后端登录态解析当前学生身份，所以学生只能查自己。管理员如果要查全量数据，必须走独立的 `/system/admin/edu/**` 接口，不经过学生工具链。再往后，我又补了 SSE 生命周期管理，保证断连后能释放 `Flux Disposable` 或取消 `Future`，前端也可以主动停止请求。知识库这块，我把删除补成“删向量、删 OSS、删 DB”的最小闭环，并真实验证了失败场景。这些内容都比“接一个大模型接口”更能体现后端工程能力。

### 2.3 2 分钟版
这个项目我更愿意把它定义成“工程化 AI 应用后端”，而不是普通 AI demo。因为普通 demo 往往只关心模型能不能回一句话，但这个项目里真正难的是，怎么把 AI 能力接进真实业务，而且不把权限边界和稳定性做坏。

第一条主线是公共知识问答。我基于现有校园场景接了 RAG，文档先上传到 OSS，再做解析、切块、向量化，问答时先检索相关片段，再把这些依据拼进 Prompt，让模型回答尽量基于校内知识，而不是完全靠通用知识硬猜。

第二条主线是工具调用权限。项目里有成绩、一卡通余额这类敏感数据，所以我先把 `public chat`、`student chat`、`admin API` 三条链路拆开。`public chat` 不注册个人工具，只做公共问答；`student chat` 才允许成绩和一卡通工具；管理员要查任意学生数据，必须走独立 `/system/admin/edu/**` 接口。再往下，工具层也不信任前端或模型传进来的 `studentId`，而是统一通过 `CurrentStudentService` 从当前登录态拿学生身份，所以模型只能决定“查什么”，不能决定“查谁”。这块我做过真实运行时验证，包括 `studentA` 诱导查询 `studentB`，最终工具层拿到的还是 `studentA` 的 `studentId`。

第三条主线是稳定性和数据生命周期。SSE 这块，我补了生命周期管理，`public / legacy chat` 断连时会释放 `Flux Disposable`，`student chat` 当前是单次工具分发加单条 SSE 回推，所以断连时会取消异步 `Future`。前端也接了 `AbortController`，可以停止生成、重复发送时抢占旧请求、页面离开时主动中止。知识库这块，我把删除补成“向量、OSS、DB”的最小闭环，并验证了 `docId` 不存在、`fileUrl` 为空这类失败场景。这里我不会夸大成完整成功链路都跑通了，因为本地 OSS 凭证不可用，完整“上传-检索-删除-再检索”还没有完成运行时闭环。

## 3. 简历项目描述扩写

### 3.1 极稳版

- 拆分 `public chat / student chat / admin API` 三条入口，解决公共问答和个人数据查询混用的越权风险，技术点：RuoYi 接口分层、角色鉴权、链路隔离；证据/限制：学生/管理员 REST 权限链路已完成运行时验证。
- 重构学生身份解析链路，统一通过后端登录态获取当前学生身份，解决前端或模型伪造 `studentId` 的问题，技术点：`student.user_id -> sys_user.user_id` 绑定、`CurrentStudentService`、MyBatis；证据/限制：学生查自己链路已真实验证，不写前端传参可信。
- 将成绩和一卡通做成学生工具，仅在 `student chat` 注册，解决公共入口暴露个人工具的问题，技术点：Spring AI Function Calling、ToolContext、工具去身份化；证据/限制：`studentA` 诱导查询 `studentB` 已有运行时日志证据，当前不是逐 token 工具流。

- 实现知识库删除最小闭环，删除时先删向量、再删 OSS、最后删 DB，解决文档删除后外部资源残留的问题，技术点：Redis Vector Store metadata 删除、OSS 删除、失败阻断；证据/限制：失败场景已验证，完整成功链路未完成运行时验收。

### 3.2 平衡版

- 基于 `RuoYi + Spring Boot + Spring AI` 落地校园智能问答后端，覆盖公共知识问答、学生个人工具问答和管理员全量查询，解决 AI 能力接入真实业务后的权限混线问题，技术点：Spring AI、RuoYi、MyBatis；证据/限制：三条链路均有代码和测试文档支撑。

### 4.3 90 秒讲解稿

这张图我一般先按三层讲。左边是前端，有 `chat.vue` 和 `edu-tools.vue`，聊天页还带了 `AbortController`，可以主动中止 SSE。中间是三条入口：`public chat` 只做公共问答，`student chat` 才允许个人工具，`admin API` 则是管理员独立查询接口。这里最关键的是学生和管理员链路先在入口层拆开，不让高权限能力混进自然语言入口。

再往右是权限和问答核心。学生聊天先经过 `CurrentStudentService` 解析当前登录学生身份，再决定是否调用成绩和一卡通工具。公共和学生聊天都可以走 RAG，还会把会话历史放到 `Redis ChatMemory`。底层存储里，MySQL 放业务真相，Redis Vector Store 放知识切片，OSS 放知识库源文件。最后模型结果通过 SSE 回推给前端，前端如果点击停止生成或者离开页面，会用 `AbortController` 把请求中断。整张图的核心边界就是：模型负责理解问题，后端负责权限、数据和生命周期。

### 4.4 3 分钟展开版

如果面试官愿意多听一点，我会从“为什么要这样拆”来讲。最左边是两个前端页面：`chat.vue` 是聊天页，承担公共问答和学生问答；`edu-tools.vue` 是管理员教务查询页。这里我不会把所有能力都塞进一个入口，因为不同入口的信任等级不一样。

中间第一层是三条 Controller 入口。`public chat` 面向公共问题，比如校规、流程、办事说明；这条链路不注册个人工具。`student chat` 面向学生本人数据，比如成绩和一卡通余额；只有这条链路才允许调用学生工具。管理员如果要查任意学生数据，不走聊天，而是走 `/system/admin/edu/**` 这条独立后台接口。这样入口层先把权限边界切开，后面的实现才不会混。

中间第二层是权限与工具收口。`student chat` 进来后，不会信任前端或者模型传来的 `studentId`，而是统一交给 `CurrentStudentService` 去解析当前登录学生身份。工具层只接收课程名这类业务参数，不接收身份参数，所以模型最多决定“查什么”，不能决定“查谁”。这是 studentA 诱导查询 studentB 还能只查回 studentA 自己数据的关键。

中间第三层是问答能力本身。公共和学生聊天都可以走 RAG，RAG 会去 Redis Vector Store 检索相关知识片段，再把这些上下文拼成系统提示词喂给模型。聊天上下文则放到 Redis ChatMemory，用 `conversationId` 关联多轮对话。这样系统既能做公共知识问答，也能带上下文。

右侧是数据层。MySQL 是成绩、一卡通、学生绑定关系和知识文档记录的真相源；Redis Vector Store 放向量切片，服务 RAG；OSS 放源文件，既服务文档导入，也参与删除链路。最后最上面再补一条 `SSE` 回前端，说明输出是流式的。前端用 `AbortController` 控制停止生成、重复发送中止旧请求和页面离开中止请求；后端则在断连时释放 `Flux Disposable` 或取消 `Future`。整个系统的边界可以一句话总结：模型只负责理解和生成，权限、身份、数据读写和资源治理全部由后端控制。

## 5. 核心链路逐条讲解

### 5.1 公共 RAG 问答链路

- 一句话概括：公共问题走 `public chat`，做 RAG 检索增强，通过 SSE 把回答流式回推给前端。
- 请求入口：`POST /api/ai/chat/public/stream`
- 核心类/模块：`SseChatController`、`RagService`、`RedisChatMemory`、`chat.vue`
- 数据怎么流转：前端发起问题和 `conversationId` -> Controller 解析请求 -> `RagService` 检索相关文档 -> 拼接系统提示词 -> `ChatClient.stream().chatResponse()` 调模型 -> 结果通过 `SseEmitter` 流式回推。
- 权限边界在哪里：`public chat` 不注册学生个人工具，不允许进入成绩/一卡通工具链。
- 已验证证据：`docs/security-test.md` 已覆盖“未登录访问公共聊天成功”“未登录询问成绩不会触发学生工具”；`docs/benchmark.md` 明确该入口用途；代码可落到 `SseChatController.java`。
- 当前限制：可以讲“公共 RAG 问答链路存在”，不能讲检索效果量化数据，也不能报首字响应具体数值。
- 面试推荐说法：公共问答入口只做知识型问答，不接敏感个人工具，先把权限边界在入口层切开，再做 RAG 和流式返回。
- 面试危险说法：公共聊天也能顺带查成绩，只是前端没放按钮。

### 5.2 学生个人工具问答链路

- 一句话概括：学生问成绩或一卡通时，`student chat` 会在后端绑定当前登录学生身份，再通过工具返回本人结果。
- 请求入口：`POST /api/ai/chat/student/stream`
- 核心类/模块：`SseChatController`、`CurrentStudentService`、`EduAiFunctionConfig`、`chat.vue`
- 数据怎么流转：学生 token 进入 `student chat` -> 校验学生角色 -> `CurrentStudentService` 解析当前学生 -> 构建 `toolContext` -> 注册成绩/一卡通工具 -> 工具执行时再取当前学生 `studentId` -> 查询 MySQL -> 通过 SSE 回推结果。
- 权限边界在哪里：学生入口必须登录且有学生角色；工具层不接收身份参数；最终 `studentId` 由后端登录态决定。
- 已验证证据：`docs/security-test.md` 中 `studentA` 查询本人、追加 `studentId` 参数无效、未绑定学生身份拒绝等场景已验证；`EduAiFunctionConfig.java` 中工具明确通过 `requireCurrentStudentId(toolContext)` 取身份。
- 当前限制：当前 student chat 是“单次工具分发 + SSE 单条回推”，不是逐 token 工具流。
- 面试推荐说法：学生个人数据查询的核心不是把工具调起来，而是把身份绑定死在后端登录态，让模型只能决定查什么，不能决定查谁。
- 面试危险说法：student chat 已经是完整 agent，模型可以自由编排多个工具并逐 token 输出。

### 5.3 管理员全量查询链路

- 一句话概括：管理员查询任意学生成绩或余额，必须走独立后台接口，不进入学生工具链。
- 请求入口：`GET /system/admin/edu/score`、`GET /system/admin/edu/card/balance`
- 核心类/模块：`AdminEduController`、`StudentMapper`、`StudentScoreMapper`、`CampusCardMapper`、`edu-tools.vue`
- 数据怎么流转：管理员页面输入 `studentId` -> 调后台接口 -> `@PreAuthorize("@ss.hasRole('admin')")` 校验 -> 先查学生基本信息 -> 再查成绩或余额 -> 返回 `AjaxResult`。
- 权限边界在哪里：管理员能力只挂在 `/system/admin/edu/**`；不复用学生自助接口；不进入学生 Function Calling 工具链。
- 已验证证据：`docs/security-test.md` 中 admin 查询 studentA、studentB 成功，studentA、studentB、普通用户、匿名访问管理员接口失败；代码可落到 `AdminEduController.java`。
- 当前限制：可以讲接口已运行时验证；不能把部分 `AjaxResult` 语义说成 HTTP 状态码已完全规范统一。
- 面试推荐说法：管理员查全量是高权限后台能力，所以我故意把它和学生自然语言入口彻底拆开。
- 面试危险说法：管理员其实也能复用学生工具，只是我额外做了个页面。

### 5.4 studentA 诱导查询 studentB 的防越权链路

- 一句话概括：即使提示词里出现 `studentB` 的学号，工具层最终仍只会查询 `studentA` 本人数据。
- 请求入口：`POST /api/ai/chat/student/stream`
- 核心类/模块：`SseChatController`、`CurrentStudentService`、`EduAiFunctionConfig`
- 数据怎么流转：`studentA` 带 token 发起恶意提示词 -> `student chat` 构建 `toolContext={currentStudentId=202301010001}` -> 工具执行时调用 `requireCurrentStudentId(toolContext)` -> MySQL 按 `studentA` 的 `studentId` 查询 -> 返回的仍然是 `studentA` 成绩。
- 权限边界在哪里：模型输入只能影响查询主题，不能影响身份解析；真正身份边界在 `CurrentStudentService` 和 `toolContext`。
- 已验证证据：`docs/security-test.md` 已记录固定提示词 A-E；运行时日志显示 `Tool getStudentScore invoked, studentId=202301010001`；返回为 `studentA` 的 `95` 分。
- 当前限制：当前验证口径是明确成绩/余额意图场景，不要说成任意复杂 agent 推理都已全面验证。
- 面试推荐说法：我拿真实学生 token 做过越权诱导测试，提示词里虽然出现了另一个学生学号，但工具层最终还是只拿到当前登录学生身份。
- 面试危险说法：模型自己识别出了这是越权请求，所以没有查。

### 5.5 SSE 正常流式响应链路

- 一句话概括：聊天请求建立 SSE 连接后，后端按链路类型持续回推内容，前端边收边展示。
- 请求入口：`POST /api/ai/chat/public/stream`、`POST /api/ai/chat/student/stream`
- 核心类/模块：`SseChatController`、`SseEmitter`、`chat.vue`、`RedisChatMemory`
- 数据怎么流转：前端发起请求并携带 `conversationId` -> 后端创建 `SseEmitter` -> 公共链路订阅 `Flux<ChatResponse>` 计算 delta 持续发送；学生链路在单次工具结果或单次调用完成后发送结果 -> 前端按 SSE chunk 解析并拼接文本。
- 权限边界在哪里：公共链路和学生链路在入口层分开；学生链路进入前先做学生角色校验。
- 已验证证据：`chat.vue` 已实现 SSE 消费和 `AbortController`；`docs/benchmark.md`、`docs/security-test.md` 记录了正常访问与页面行为。
- 当前限制：student chat 当前不是逐 token 工具流；公共链路可以流式增量，学生链路更多是单条结果回推。
- 面试推荐说法：SSE 在这个项目里主要解决的是“边生成边展示”和“可中途取消”，不同链路的流式粒度不完全一样。
- 面试危险说法：所有聊天入口都是完全一致的 token 级流式工具输出。

### 5.6 SSE 断连取消链路

- 一句话概括：客户端断连、超时、异常或主动 abort 时，后端统一关闭生命周期并取消上游资源。
- 请求入口：所有 SSE 聊天入口
- 核心类/模块：`SseChatController` 中的 `StreamLifecycle`、`chat.vue` 的 `AbortController`
- 数据怎么流转：请求建立时记录 `SseEmitter`、`Disposable`、`Future` -> 发生超时/异常/完成/客户端断开时进入统一 close -> `public / legacy chat` 尝试 `dispose` 上游 `Flux` -> `student chat` 尝试 `cancel Future` -> 前端停止读取并停止拼接。
- 权限边界在哪里：这条链路不改变权限模型，只是资源治理；断连取消后也不影响学生/管理员原有边界。
- 已验证证据：`docs/benchmark.md` 和 `docs/security-test.md` 记录 `disposableDisposed=true`、`futureCancelled=true`、`AbortController` 生效；代码可落到 `SseChatController.java` 和 `chat.vue`。
- 当前限制：已做单连接运行时验收；未完成真实高并发、多轮次量化压测。
- 面试推荐说法：这轮优化的重点不是性能数字，而是让断开的流式请求真的能把上游资源收回来。
- 面试危险说法：我已经证明这套 SSE 能稳定扛住大规模并发。

### 5.7 知识库删除链路

- 一句话概括：删除知识库文档时，不只删数据库，而是按“向量 -> OSS -> DB”做最小闭环。
- 请求入口：`DELETE /system/knowledge/{docIds}`
- 核心类/模块：`KnowledgeDocController`、`KnowledgeDocServiceImpl`、`RagService`、`AliOssService`
- 数据怎么流转：收到 `docId` -> 先查 `knowledge_doc` -> 校验 `fileUrl` -> `RagService.deleteByFileUrl(fileUrl)` 删除向量 -> `AliOssService.deleteObjectByUrl(fileUrl)` 删除 OSS -> 最后删除数据库记录。
- 权限边界在哪里：删除能力挂在知识库后台权限下，不走聊天链路；内部如果外部资源删除失败，不会继续删除 DB。
- 已验证证据：`docs/knowledge-delete-test.md` 和 `KnowledgeDocServiceImpl.java` 已说明删除顺序、失败阻断、部分失败日志定位；`docId` 不存在、`fileUrl` 为空等失败场景已验证。
- 当前限制：完整“上传-检索-删除-再检索”成功链路因本地 OSS 凭证不可用尚未完成运行时验证；历史向量缺 `fileUrl` metadata 时仍会 fallback 到 `source/fileName`。
- 面试推荐说法：我能稳讲的是删除闭环代码已经落地，而且失败场景做过真实验证；成功链路不夸大到全验收。
- 面试危险说法：知识库删除已经从上传到再检索全部跑通，没有残留风险。

## 6. 重点技术点深挖

### 6.1 RAG

#### 为什么要 RAG
面试可答：
校园场景里很多问题是校内规则、流程、办事说明，这些内容不在通用模型参数里，或者会经常变化。如果只靠模型裸答，很容易泛化回答或者编内容，所以我用 RAG 先检索校内知识，再把依据拼进 Prompt，让回答尽量基于现有文档。

#### 文档为什么要存 OSS
面试可答：
OSS 在这里主要承担源文件存储，不让数据库直接承载大文件，也不把文件只放在本地磁盘。这样导入时可以从 OSS 读原文件做解析，删除时也能按 `fileUrl` 追踪并一起清理源文件。

#### MySQL / OSS / Vector Store 各自作用
面试可答：
MySQL 存业务真相和知识文档记录，比如 `docId`、`fileUrl`、状态；OSS 存原始文件；Vector Store 存切块后的向量和 metadata，服务检索。三者职责不同，所以删除时也不能只删其中一层。

#### 切块和 metadata 的意义
面试可答：
切块是为了让向量检索的粒度更合适，既不要整篇文档太粗，也不要碎到丢上下文。metadata 则是为了后续追踪来源、定位 chunk、做删除过滤，比如 `fileName`、`source`、`fileUrl`、`chunkIndex`。

#### `fileUrl` metadata 为什么重要
面试可答：
`fileUrl` 是新数据删除精度提升的关键。以前如果只靠 `source/fileName`，历史上存在同名文件时理论上有误删风险；有了 `fileUrl` 后，可以先按更稳定的资源标识做精确删除，只有历史数据缺这个字段时才走兼容 fallback。

### 6.2 Function Calling

#### 为什么不能信任模型参数
面试可答：
因为模型和用户输入本质上都属于低信任输入。只要工具允许外部直接传 `studentId`，就存在提示词诱导或者前端绕过的空间，所以身份参数不能交给模型控制。

#### 为什么工具要去身份化
面试可答：
工具去身份化的核心是把“查什么”和“查谁”拆开。模型只负责理解意图，比如成绩还是余额；真正的身份解析由后端登录态决定，这样工具才不会被拿去查别人。

#### ToolContext 如何帮助传递后端上下文
面试可答：
`student chat` 在进入工具前，会把当前学生身份写到 `toolContext`。工具执行时再从 `toolContext` 取 `currentStudentId`，这样身份不是从提示词里拿，而是从后端上下文里拿。

#### 为什么 `public chat` 不注册个人工具
面试可答：
因为 `public chat` 是低信任入口，允许匿名或普通公共问答。如果这里也注册个人工具，就等于把敏感数据能力暴露给了最外层自然语言入口。

#### 为什么管理员能力不接进 Function Calling
面试可答：
管理员查全量数据是高权限后台能力，不应该混进学生工具链或自然语言入口。否则模型一旦能触达按任意 `studentId` 查询，就会把权限边界打穿。

### 6.3 权限安全

#### `student.user_id -> sys_user.user_id` 的意义
面试可答：
这层绑定让业务学生身份和系统登录态真正连起来，后端才能从当前登录用户稳定解析出学生身份，学生自助接口和 student chat 才能共用同一套身份收口。

#### `CurrentStudentService` 的作用
面试可答：
它是学生身份解析和权限收口的核心服务。无论是学生自助接口还是工具调用，最终都通过它拿当前学生身份，而不是各处自己解析。

#### 学生查自己怎么保证
面试可答：
第一层是入口角色校验，第二层是学生自助接口不接收身份参数，第三层是工具层统一从当前登录态解析 `studentId`。所以就算手工加参数或者在提示词里写别人学号，也不会改最终查询对象。

#### 管理员查全量怎么保证
面试可答：
管理员能力单独挂在 `/system/admin/edu/**`，通过 `@PreAuthorize("@ss.hasRole('admin')")` 做角色限制，查询时显式接收 `studentId`。这条链路和学生工具链是完全分开的。

#### 前端隐藏按钮为什么不算安全边界
面试可答：
前端只能改善体验，不能当安全边界。真正的安全边界必须在后端入口、角色校验和最终数据查询处收口，否则请求照样可以被手工构造。

### 6.4 SSE

#### 为什么选 SSE
面试可答：
这里主要是服务端单向推流，不需要复杂的双向实时交互。SSE 比 WebSocket 更轻，和现有 HTTP 鉴权、前端 fetch、后端 `SseEmitter` 都更容易整合。

#### `public/legacy` 和 `student chat` 的差异
面试可答：
`public / legacy chat` 当前是基于 `Flux` 的增量流式输出；`student chat` 当前更偏单次工具分发和单条结果回推，所以断连时取消点也不同。

#### `Flux Disposable` 是什么
面试可答：
它可以理解成对上游 Reactor 订阅的控制句柄。SSE 断连后如果不 dispose，上游可能还在继续产出数据，导致无效资源消耗。

#### `CompletableFuture cancel` 的意义
面试可答：
student chat 当前是异步任务跑完再回推结果，如果用户已经断开，这个异步任务继续跑就没有价值，所以要尝试 `cancel Future` 并阻止后续回推。

#### `AbortController` 的意义
面试可答：
它让前端不必被动等后端结束，用户可以点击停止生成、重复发送时抢占旧请求、页面离开时主动中断，前后端一起把流式请求关干净。

#### 为什么断连后要取消上游
面试可答：
因为连接已经没了，后面继续生成的内容用户也收不到。断连后不取消上游，只会浪费线程、模型调用和内存资源。

### 6.5 知识库删除

#### 为什么不能只删数据库
面试可答：
如果只删数据库，OSS 里源文件还在，Vector Store 里的切片也还在，被删文档仍可能被检索到，这样业务记录没了，但外部资源残留，状态反而更乱。

#### 为什么删除顺序是“向量 -> OSS -> DB”
面试可答：
核心思路是外部资源先删，业务记录最后删。这样一旦外部资源删除失败，数据库记录还在，后续还能追踪和重试；如果先删 DB，失败后反而更难定位。

#### 为什么优先 `fileUrl` 删除向量
面试可答：
`fileUrl` 比 `fileName/source` 更接近资源唯一标识，删除精度更高。特别是历史上可能存在同名文件时，优先 `fileUrl` 能明显降低误删风险。

#### fallback `source/fileName` 的风险
面试可答：
它是历史兼容路径，不是理想路径。风险在于如果历史向量没有 `fileUrl` metadata，且存在同名文件，理论上可能误删同名文档对应的向量。

#### 为什么不做分布式事务
面试可答：
OSS 和向量库不在同一个本地事务里，硬做强一致事务成本高、复杂度也高。当前更现实的方案是“尽力删除 + 失败阻断 + 日志留痕 + DB 最后删”。

#### 当前未完成完整成功链路验收怎么诚实回答
面试可答：
我会明确区分两件事：第一，删除闭环代码已经实现；第二，失败场景已经做过真实验证；但完整“上传-检索-删除-再检索”成功链路，因为本地 OSS 环境限制，还没有完成运行时闭环，所以我不会讲成已全验收。

## 9. 面试场景模拟回答

### 9.1 面试官：你介绍一下这个项目
- 结论：这是一个做了工程化补强的校园 AI 应用后端，不是普通聊天 demo。

- 证据：权限链路、studentA 诱导越权、SSE 断连取消都有运行时验证，删除闭环有代码实现和失败场景验证。
- 限制或优化：我不会把它讲成完整 agent，也不会把删除成功链路讲成已全验收。

### 9.2 面试官：你这个项目最大亮点是什么？
- 结论：最大亮点是把 AI 能力接进真实业务时，权限边界没有被做坏。
- 实现：我把学生工具做成去身份化调用，模型只能决定查什么，不能决定查谁；管理员能力也没有混进学生工具链。
- 证据：`studentA` 诱导查 `studentB` 时，工具层最终还是 `studentA` 的 `studentId`。
- 限制或优化：当前 student chat 还是单次工具分发，不讲成完整逐 token 工具流。

### 9.3 面试官：你怎么防止大模型查别人数据？
- 结论：核心不是提示词拦截，而是后端不信任模型传入身份参数。
- 实现：学生工具不接收 `studentId`，最终身份统一由 `CurrentStudentService` 从当前登录态解析，并通过 `toolContext` 传给工具。
- 证据：我做过 `studentA` 诱导查询 `studentB` 的运行时测试，工具层拿到的仍是 `studentA` 身份。
- 限制或优化：这套口径当前针对学生链路最稳，管理员能力仍刻意放在独立后台接口。

### 9.4 面试官：为什么要把 public chat 和 student chat 拆开？
- 结论：因为两条入口的信任级别不同，不能混。
- 实现：`public chat` 只做公共问答，不注册个人工具；`student chat` 才允许成绩和一卡通工具。
- 证据：未登录或公共入口问成绩时，不会触发学生工具，测试文档有对应用例。
- 限制或优化：这是一层入口边界，不替代后端工具层的身份收口。

### 9.5 面试官：管理员为什么不走 Function Calling？
- 结论：因为管理员查全量是高权限后台能力，不应该挂到低信任自然语言入口。
- 实现：管理员独立走 `/system/admin/edu/**`，通过 `admin` 角色校验，再按 `studentId` 查成绩或余额。
- 证据：admin 可查 studentA、studentB，学生和普通用户打这条接口会失败。
- 限制或优化：如果以后要做管理员自然语言查询，也应该新做高信任后台入口，不直接复用学生工具链。

### 9.6 面试官：SSE 断连后怎么处理？
- 结论：断连后会统一 close 生命周期，并尝试取消上游资源。
- 实现：后端统一管理 `SseEmitter`、`Disposable` 和 `Future`，前端则通过 `AbortController` 主动中止请求。
- 证据：`public / legacy chat` 断连日志里有 `disposableDisposed=true`，`student chat` 有 `futureCancelled=true`。
- 限制或优化：当前是单连接运行时验证，不代表已经做完并发压测。

### 9.7 面试官：你怎么证明断连取消真的生效？

### 9.8 面试官：OSS 在项目里到底有什么用？

- 关键词：入口隔离、信任级别、角色边界

- 关键词：校内知识、依据、降幻觉
- 不能说的话：RAG 已经把准确率提升到某个数字。

- 不能说的话：OSS 只是摆设。

- 必背问题：public/legacy 和 student chat 的流式差异是什么？
- 30 秒回答：public/legacy 更像连续模型流，student chat 当前是单次工具分发和单条结果回推，所以取消方式和流式粒度都不同。
- 关键词：Flux、Future、流式粒度
- 不能说的话：两条链路完全一样。

### 卡片 20
- 卡片标题：Flux Disposable
- 必背问题：`Disposable` 是什么？
- 30 秒回答：它是上游 Reactor 订阅的控制句柄，SSE 断开后需要 dispose，不然上游还会继续产出无效数据。
- 关键词：订阅句柄、上游取消、无效产出
- 不能说的话：就是一个普通变量。

### 卡片 21
- 卡片标题：Future cancel
- 必背问题：为什么要 `cancel Future`？
- 30 秒回答：student chat 当前是异步任务跑完再回推结果，用户断开后这个任务继续跑没有意义，所以要尝试取消并阻止后续回推。
- 关键词：异步任务、断连取消、阻止回推
- 不能说的话：断开后 Future 自己会停。

### 卡片 22
- 卡片标题：AbortController
- 必背问题：`AbortController` 的作用是什么？
- 30 秒回答：它让前端可以主动停止生成、重复发送时中止旧请求、页面离开时中止请求，和后端生命周期管理形成配合。
- 关键词：停止生成、抢占旧请求、页面离开
- 不能说的话：只是个前端小优化。

### 卡片 23
- 卡片标题：断连取消证据
- 必背问题：你怎么证明断连取消真的生效？
- 30 秒回答：public/legacy 断连后日志里有 `disposableDisposed=true`，student chat 断连后有 `futureCancelled=true`，前端旧响应也会停止拼接。
- 关键词：日志证据、disposed、cancelled
- 不能说的话：代码里写了所以肯定生效。

### 卡片 24
- 卡片标题：不能只删数据库
- 必背问题：为什么不能只删数据库记录？
- 30 秒回答：只删数据库会留下向量切片和 OSS 源文件残留，被删文档仍可能被检索到，状态也会不一致。
- 关键词：外部资源残留、状态不一致
- 不能说的话：删表就算删干净了。

### 卡片 25
- 卡片标题：删除顺序
- 必背问题：为什么删除顺序是“向量 -> OSS -> DB”？
- 30 秒回答：因为外部资源先删、数据库最后删，失败时还能保留记录方便追踪和重试，不会先把索引信息删没。
- 关键词：外部先删、DB 最后删、可追踪
- 不能说的话：顺序无所谓。

- 关键词：实现、失败场景、不能夸大
- 不能说的话：完整删除闭环已经全跑通。
