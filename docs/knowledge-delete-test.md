# 知识库删除闭环测试说明

## 1. 目标

验证知识库文档删除时，数据库、OSS 源文件、Redis Vector Store 三层能否形成最小闭环。

## 2. 当前实现

删除流程采用“外部资源先删，数据库最后删”：

1. 查询 `knowledge_doc`
2. 根据 `fileUrl` 删除向量数据
3. 根据 `fileUrl` 删除 OSS 对象
4. 删除数据库记录

## 3. 测试点

1. 上传测试文档并完成向量化
2. 验证数据库里存在 `knowledge_doc` 记录
3. 验证提问时可以检索到该文档内容
4. 删除该文档
5. 验证后端日志出现向量删除日志
6. 验证后端日志出现 OSS 删除日志
7. 验证数据库记录被删除
8. 再次提问，不应再检索到该文档内容
9. 删除不存在 `docId` 时，应返回明确错误
10. OSS 删除失败时，不应静默成功
11. 向量删除失败时，不应静默成功
12. 批量删除部分失败时，应能通过日志定位失败 `docId`

## 4. 局限

当前没有引入分布式事务，因此这是“尽力删除 + 日志记录 + DB 最后删除”的一致性治理方案，不是强事务方案。

当前最小闭环还依赖已有向量 metadata：

1. 旧数据主要依赖 `source/fileName` 做删除过滤
2. 如果历史上存在同名文件，理论上可能出现同名文档被一起删向量的风险
3. 新导入数据已经补写 `fileUrl` metadata，后续可以优先按 `fileUrl` 做更精确删除
## 6. 删除精度修正（2026-05-23）

本轮又补了一次删除精度修正：

1. 新导入数据已经写入 `fileUrl` metadata。
2. 删除时优先按 `fileUrl` 做精确删除。
3. 只有当历史数据缺少 `fileUrl` metadata，或者按 `fileUrl` 删除失败时，才 fallback 到 `source/fileName`。
4. fallback 会记录 warning 日志，明确提示这是历史数据兼容路径，存在同名文件误删风险。

长期最优方案：

1. 每个 chunk metadata 里都写入 `docId`。
2. 删除时优先按 `docId` 删除。
3. 如果后续做历史向量迁移，应补齐 `fileUrl/docId` metadata。
