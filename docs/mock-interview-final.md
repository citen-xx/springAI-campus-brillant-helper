# 校园智能知识库助手最终高压模拟面试稿

## 1. 开场说明

这份文档的用途是面试前最后一轮训练，不再扩展新内容，只把当前项目里最值得讲、最容易被追问、最容易讲重的部分收口成一份高压模拟稿。

本稿重点服务 5 件事：
- 强化 1 分钟项目介绍
- 强化白板画图
- 强化高压追问
- 强化风险口径
- 强化不能夸大的边界

使用方法建议：
- 先背第 2 节项目介绍终版
- 再练第 3 节白板讲解
- 然后按第 4、5、6 节连续做三轮模拟
- 最后只看第 8、9 节做面试前速记

底线提醒：
- student chat 当前只能讲“单次工具分发 + SSE 单条回推”
- 删除闭环只能讲“代码实现 + 失败场景验证”
- 没有真实压测报告，不能讲并发、QPS、P99、首字响应等具体数据
- HTTP 权限失败语义不能讲成已经完全 REST 规范化

## 2. 1 分钟项目介绍终版

### 2.1 1 分钟终版

这个项目是一个校园智能知识库助手后端，但我做的重点不是单纯接一个大模型接口，而是把 AI 能力安全接进真实业务系统里。公共问答这条链路我接了 RAG，把校内文档放到知识库里，问答时先检索再组装上下文。个人数据这条链路我用了 Function Calling，把成绩和一卡通做成工具，但工具层不信任前端或模型传入的 `studentId`，而是统一通过后端登录态解析当前学生身份，所以学生只能查自己。管理员如果要查任意学生数据，必须走独立 `/system/admin/edu/**` 接口，不进入学生工具链。除此之外，我还补了 SSE 生命周期管理，断连时 `public / legacy chat` 会释放 `Flux Disposable`，`student chat` 会取消 `Future`，前端也通过 `AbortController` 支持停止生成和中止旧请求。知识库删除这块，我补成了“先删向量、再删 OSS、最后删 DB”的最小闭环，并验证了失败场景。这个项目不是普通 AI demo，而是 AI 应用后端工程化补强。

### 2.2 30 秒压缩版

这个项目不是普通 AI demo，而是我把 AI 能力接进校园业务系统后做的一轮工程化补强。公共问答走 RAG，学生问答走 Function Calling，但工具层不信任模型传入的 `studentId`，学生只能查自己；管理员查全量则走独立后台接口。我还补了 SSE 断连取消和知识库删除最小闭环，重点体现的是权限、安全边界、稳定性和数据生命周期治理。

### 2.3 2 分钟展开版

这个项目我不会讲成“我做了一个聊天机器人”，因为它更像一个 AI 应用后端工程题。项目里有两类核心需求，一类是公共知识问答，比如校规、办事流程；另一类是敏感个人数据查询，比如成绩和一卡通余额。我的工作重点就是把这两类能力接进同一个系统里，但又不能把权限边界做坏。

第一块是公共问答。我基于现有校园知识做了 RAG，文档先上传到 OSS，再做解析、切块、向量化，问答时先检索相关片段，再把这些内容拼进系统提示词，让模型回答尽量有依据，而不是完全靠通用知识硬猜。

第二块是工具调用权限。这块我先把 `public chat`、`student chat` 和 `admin API` 三条链路拆开。`public chat` 不注册个人工具，只做公共问答；`student chat` 才允许成绩和一卡通工具；管理员要查任意学生数据，必须走独立 `/system/admin/edu/**` 接口。再往下，工具层也不信任前端或模型传入的 `studentId`，而是统一通过 `CurrentStudentService` 从当前登录态解析学生身份，所以模型只能决定“查什么”，不能决定“查谁”。这条链路我做过真实验证，`studentA` 诱导查询 `studentB` 时，工具层最终还是 `studentA` 的 `studentId`。

第三块是稳定性和数据生命周期。SSE 这块我补了生命周期管理，`public / legacy chat` 断连时能释放 `Flux Disposable`，`student chat` 因为当前是单次工具分发加单条 SSE 回推，所以断连时会取消异步 `Future`。前端也加了 `AbortController`，支持停止生成、重复发送中止旧请求和页面离开中止请求。知识库删除这块，我补成了“先删向量、再删 OSS、最后删 DB”的最小闭环，并验证了删除失败场景。这里我不会夸大成完整成功链路已验收，因为本地 OSS 凭证不可用，完整“上传-检索-删除-再检索”还没有完成运行时闭环。所以这个项目真正能体现的，不是模型本身，而是 AI 应用后端工程化补强。

## 3. 白板画图终版

### 3.1 90 秒白板画图讲解稿

#### 第一步：先画前端
画：
- `chat.vue`
- `edu-tools.vue`
- 在 `chat.vue` 旁边补 `AbortController`

边画边说：
左边先画两个前端入口，一个是聊天页 `chat.vue`，一个是管理员查询页 `edu-tools.vue`。聊天页除了发请求，还负责用 `AbortController` 主动停止 SSE 请求。

#### 第二步：画三条入口
在中间画三个框：
- `public chat`
- `student chat`
- `admin API`

边画边说：
中间是三条后端入口。`public chat` 只做公共问答，`student chat` 才允许个人工具，`admin API` 是管理员独立查询接口。这里的核心就是先把入口按权限边界拆开。

#### 第三步：画学生身份和工具层
在 `student chat` 下方画：
- `CurrentStudentService`
- `Function Calling tools`
  - `getStudentScore`
  - `getCardBalance`

边画边说：
学生链路进来以后，不信任模型或前端传入的 `studentId`，而是统一交给 `CurrentStudentService` 解析当前登录学生身份。工具层只负责查成绩和余额，不负责决定查谁。

#### 第四步：画问答和会话层
在 `public chat`、`student chat` 右侧画：
- `RAG`
- `Redis ChatMemory`

边画边说：
公共问答和学生聊天都可以接 RAG，先检索知识片段再组装上下文；多轮对话历史则放到 `Redis ChatMemory`。

#### 第五步：画底层存储
在最右侧或下方画：
- `MySQL`
- `Redis Vector Store`
- `OSS`

边画边说：
MySQL 是业务真相源，存学生、成绩、一卡通和文档记录；Redis Vector Store 存知识切片；OSS 存知识库源文件，既服务导入，也参与删除链路。

#### 第六步：画返回链路
从 `public chat` 和 `student chat` 往左画回前端：
- `SSE`

边画边说：
最后结果通过 SSE 回推给前端。`public / legacy chat` 当前是增量流式输出，`student chat` 当前更偏单次工具分发和单条结果回推。

#### 最后一口总结
模型负责理解问题，身份、权限、数据读写、资源释放和删除一致性都由后端控制。

### 3.2 3 分钟白板展开版

我一般会按“入口层、能力层、数据层”三层来画。最左边是前端，我先画 `chat.vue` 和 `edu-tools.vue`。`chat.vue` 承担公共问答和学生问答，旁边我会补一个 `AbortController`，因为前端可以停止生成、重复发送时中止旧请求、页面离开时主动取消请求。`edu-tools.vue` 则是管理员查询页。

中间第一层我会画三条入口：`public chat`、`student chat`、`admin API`。这里要先讲一个原则，不同信任级别的能力不能共用一个入口。`public chat` 只做公共知识问答，不注册个人工具；`student chat` 才允许查成绩和一卡通；管理员查全量数据不能走聊天，而是走独立 `/system/admin/edu/**` 接口。入口先拆开，后面才不会混权限。

中间第二层我会画学生身份和工具层，也就是 `CurrentStudentService` 和 `Function Calling tools`。这块是整个权限边界的关键。学生工具不信任前端或模型传来的 `studentId`，而是统一通过 `CurrentStudentService` 从当前登录态解析学生身份，再把这个身份带进工具执行上下文。所以模型能决定“查成绩”还是“查余额”，但不能决定“查哪个学生”。这也是为什么 `studentA` 诱导查询 `studentB` 时，最后查出来的还是 `studentA` 本人的数据。

中间第三层我会画 `RAG` 和 `Redis ChatMemory`。RAG 负责知识检索增强，先从知识库里拿到相关片段，再把上下文拼进提示词里；`Redis ChatMemory` 则负责多轮对话上下文，让系统记住同一个 `conversationId` 下的历史消息。

最右边或底层我会画三个存储：`MySQL`、`Redis Vector Store`、`OSS`。MySQL 是业务真相源，存学生、成绩、一卡通、知识库文档记录这些结构化数据；Redis Vector Store 存向量切片，服务 RAG 检索；OSS 存源文件，导入时从 OSS 读文件做解析，删除时也要联动 OSS 删除源文件。这里顺便能引出删除闭环：不是只删数据库，而是“向量 -> OSS -> DB”。

最后我会从 `public chat` 和 `student chat` 画一条 `SSE` 回到 `chat.vue`。这时候补一句：后端统一管理 SSE 生命周期，`public / legacy chat` 断连时释放 `Flux Disposable`，`student chat` 当前因为是单次工具分发，所以断连时取消异步 `Future`；前端则用 `AbortController` 主动中止请求。最后一句话总结全图：模型负责理解问题，身份、权限、数据读写、资源释放和删除一致性都由后端控制。

## 4. 第一轮模拟面试：正常技术面

### 4.1
- 面试官问题：你先介绍一下这个项目。
- 我的推荐回答：这是一个校园智能知识库助手后端，但我做的重点不是简单接模型，而是把公共 RAG 问答、学生个人工具问答和管理员全量查询接进同一个系统后，把权限边界、SSE 生命周期和知识库删除闭环补实。
- 回答关键词：工程化、RAG、工具调用、权限边界、SSE、删除闭环
- 不能说的话：这是完整 agent 平台。
- 追问方向：那你具体做了哪些补强？

### 4.2
- 面试官问题：这个项目最核心的设计点是什么？
- 我的推荐回答：最核心的是把 `public chat`、`student chat`、`admin API` 三条链路先拆开，不让不同信任级别的能力混在一起。
- 回答关键词：三链路、信任级别、入口隔离
- 不能说的话：只是为了前端页面清晰。
- 追问方向：为什么不能共用一个入口？

### 4.3
- 面试官问题：为什么要做 RAG？
- 我的推荐回答：因为校园问题里很多是校内规则和流程，通用模型不一定知道或者容易泛化，所以我让系统先检索知识片段，再把依据拼进回答上下文。
- 回答关键词：校内知识、检索增强、依据
- 不能说的话：RAG 已经显著提升了准确率多少。
- 追问方向：具体链路怎么走？

### 4.4
- 面试官问题：你的知识库链路是什么？
- 我的推荐回答：文档先上传到 OSS，再做解析、切块、向量化，写进 Redis Vector Store；问答时先检索相关片段，再组装系统提示词调模型。
- 回答关键词：OSS、切块、向量化、检索、Prompt
- 不能说的话：模型直接读 OSS。
- 追问方向：为什么要切块？

### 4.5
- 面试官问题：为什么学生个人数据不用普通接口直接调，而要走 Function Calling？
- 我的推荐回答：因为学生是在自然语言场景里提问，Function Calling 适合把“查成绩”“查余额”这种意图转成受控工具调用，但关键不是能调工具，而是工具层不能信任外部身份参数。
- 回答关键词：自然语言意图、受控工具、身份参数
- 不能说的话：因为 Function Calling 比普通接口更高级。
- 追问方向：为什么不能信任模型参数？

### 4.6
- 面试官问题：你为什么不信任模型传来的 `studentId`？
- 我的推荐回答：因为模型和用户输入本质上都属于低信任输入，只要允许外部直接决定 `studentId`，就存在越权空间，所以最终查询身份必须由后端登录态决定。
- 回答关键词：低信任输入、越权风险、后端登录态
- 不能说的话：模型一般不会乱传。
- 追问方向：那你具体怎么实现？

### 4.7
- 面试官问题：`CurrentStudentService` 在这里起什么作用？
- 我的推荐回答：它是学生身份解析的统一收口点，学生自助接口和工具调用最后都通过它从当前登录用户解析出学生身份。
- 回答关键词：身份收口、统一解析、登录态绑定
- 不能说的话：只是普通工具类。
- 追问方向：`student.user_id -> sys_user.user_id` 绑定有什么意义？

### 4.8
- 面试官问题：学生为什么只能查自己？
- 我的推荐回答：因为入口层先做学生角色校验，接口和工具都不信外部 `studentId`，最终身份统一通过 `CurrentStudentService` 从当前登录态解析，所以手工拼参数和提示词诱导都改不了查询对象。
- 回答关键词：角色校验、后端决定身份、多层收口
- 不能说的话：主要靠前端不传学号。
- 追问方向：有没有真实越权测试？

### 4.9
- 面试官问题：管理员为什么能查全量？
- 我的推荐回答：管理员查全量是独立后台能力，挂在 `/system/admin/edu/**` 接口上，通过 `admin` 角色校验后按 `studentId` 查询，不走学生工具链。
- 回答关键词：独立接口、admin 角色、后台能力
- 不能说的话：管理员其实也走 student chat。
- 追问方向：为什么不把管理员也接进 Function Calling？

### 4.10
- 面试官问题：你怎么证明 `studentA` 查不到 `studentB`？
- 我的推荐回答：我做过真实运行时验证，`studentA` 用带 `studentB` 学号的诱导提示词发起 student chat，请求最终工具层日志还是 `studentId=202301010001`，返回的也是 `studentA` 本人的成绩。
- 回答关键词：运行时验证、日志证据、studentId 收口
- 不能说的话：模型自己判断了越权。
- 追问方向：这个身份是怎么传到工具里的？

### 4.11
- 面试官问题：ToolContext 在项目里怎么用？
- 我的推荐回答：student chat 会先把当前学生身份写进 `toolContext`，工具执行时从 `toolContext` 取 `currentStudentId`，而不是从提示词里拿身份。
- 回答关键词：toolContext、currentStudentId、后端上下文
- 不能说的话：ToolContext 只是给模型看的提示。
- 追问方向：ToolContext 会不会被伪造？

### 4.12
- 面试官问题：为什么 `public chat` 不注册个人工具？
- 我的推荐回答：因为 `public chat` 是低信任入口，只能做公共问答。如果在这里注册个人工具，就等于把敏感数据能力暴露给最外层自然语言入口。
- 回答关键词：低信任入口、最小授权、工具隔离
- 不能说的话：只是暂时没做。
- 追问方向：那 public chat 问成绩时会怎样？

### 4.13
- 面试官问题：student chat 现在到底是什么形态？
- 我的推荐回答：当前最准确的说法是“单次工具分发 + SSE 单条回推”，重点先保证权限闭环和稳定性，不把它讲成逐 token 工具流。
- 回答关键词：单次工具分发、单条回推、不是逐 token
- 不能说的话：已经是完整 agent。
- 追问方向：为什么不继续做成完整 agent？

### 4.14
- 面试官问题：为什么这里选 SSE？
- 我的推荐回答：因为这里主要是服务端单向推流，不需要复杂的双向实时通信，SSE 和现有 HTTP 鉴权、前端 fetch、后端 `SseEmitter` 更匹配。
- 回答关键词：单向推流、SseEmitter、HTTP
- 不能说的话：因为不会 WebSocket。
- 追问方向：student chat 和 public chat 的流式区别是什么？

### 4.15
- 面试官问题：你做了哪些 SSE 生命周期优化？
- 我的推荐回答：后端统一管理 `SseEmitter`、上游 `Disposable` 和异步 `Future`，断连、超时、异常或前端主动 abort 时统一 close，避免连接断了后模型还在无效生成。
- 回答关键词：生命周期、Disposable、Future、统一 close
- 不能说的话：只是补了个 try-catch。
- 追问方向：你怎么证明取消真的生效？

### 4.16
- 面试官问题：你怎么证明 SSE 断连取消生效了？
- 我的推荐回答：我做过真实断连验收，`public / legacy chat` 断连后日志里有 `disposableDisposed=true`，`student chat` 断连后有 `futureCancelled=true`，前端 `AbortController` 也验证了停止生成和中止旧请求。
- 回答关键词：disposableDisposed、futureCancelled、AbortController
- 不能说的话：代码里写了，所以肯定生效。
- 追问方向：有没有并发压测数据？

### 4.17
- 面试官问题：知识库删除闭环你做了什么？
- 我的推荐回答：我把删除补成“先删向量、再删 OSS、最后删 DB”的最小闭环，不再只删数据库记录。
- 回答关键词：向量、OSS、DB、最小闭环
- 不能说的话：只是补了个删除接口。
- 追问方向：为什么这样排序？

### 4.18
- 面试官问题：为什么删除顺序是“向量 -> OSS -> DB”？
- 我的推荐回答：核心思路是外部资源先删，数据库记录最后删。这样外部资源删除失败时，数据库记录还在，便于追踪和重试。
- 回答关键词：外部先删、DB 最后删、可追踪
- 不能说的话：顺序无所谓。
- 追问方向：为什么优先按 `fileUrl` 删除向量？

### 4.19
- 面试官问题：为什么优先按 `fileUrl` 删除向量？
- 我的推荐回答：因为 `fileUrl` 比 `source/fileName` 更接近资源标识，删除精度更高；只有历史数据缺 `fileUrl` metadata 时才走 fallback。
- 回答关键词：fileUrl-first、删除精度、fallback
- 不能说的话：这样已经彻底没有误删风险了。
- 追问方向：fallback 风险是什么？

### 4.20
- 面试官问题：这个项目还有哪些不足？
- 我的推荐回答：最明显的不足是没有真实大规模压测数据，student chat 不是完整逐 token 工具流，删除完整成功链路也没有完成运行时全验收。

## 9. 面试前 30 分钟速记版
